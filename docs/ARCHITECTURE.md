# 操作票据与技术路线

## 票据是什么

可以把它理解为“本次页面操作的通行证”。统一身份认证解决“你是谁”，业务会话维持登录，操作票据则参与这一次受保护操作的授权。只复制账号密码、Cookie或坐标，无法保证补全这条链路。

我们在已进入的浏览器页面上实际得到过：

```js
Boolean(sessionStorage.getItem('daily-checkin-operation-ticket'))
// false
```

这说明“能看见页面”与“可以提交”不同。操作票据不是可以随便编一个字符串的字段，也没有从一份抓包中证明可永久复用。

原部署通过官方微信里的小程序进入H5，核验票据存在后让现有页面完成提交。脚本只记录票据是否存在，不导出其值，也不实现独立签发算法。最新上游固件另外实现了微信授权取票链路，见[上游说明](https://github.com/richard297779/UESTC-MoonCheck/blob/3465b403884354009caff93a07c5d3345e124b15/README.md)；那是另一条路线，未在本项目实测。

## 哪些部分属于本项目

本项目提供桌面容器启动、只访问自有渲染器的调试启动器、页面定位与UI操作、结果回查、持久化防重复、QQ通知，以及备份和清理。WMPF协议桥接与基础调试能力来自WMPFDebugger，见[署名](../THIRD_PARTY_NOTICES.md)。

页面内只读查询使用学校当前前端模块，返回日期、状态和少量错误代码。真正提交仍由界面按钮触发；不直接构造签到POST。由于模块文件名和导出已固定，学校重新构建前端后需要人工核对，不能猜一个新导出继续提交。

## 定位的实际范围

H5可能从路由参数初始化地图，未必每次调用浏览器定位API。因此当前实现同时处理地图初始坐标和当前页面`navigator.geolocation`，再回读页面确认二者匹配。

WGS84是API覆盖输入；GCJ-02数组顺序为`[经度, 纬度]`，用于地图。两套坐标不能直接混用，百度BD-09分享坐标也不能原样当作GPS。

覆盖只存在于当前文档；页面重建后需重新设置。没有验证Linux系统定位提供方、原生`wx.getLocation`或其他小程序的位置被修改。

## 成功与失败如何定义

- 只在脚本时段内、业务日期正确且状态为`PENDING`时尝试提交。
- 认证、定位、票据、按钮、页面枚举或异常标记不符合要求时停止。
- 先持久化`confirmIntent`，再点击最后确认；发生崩溃或不确定响应时保留账本。
- 必须从学校今日记录回读到当天`CHECKED_IN`才标记成功；按钮点击成功、HTTP 200或没有弹窗都不足以证明成功。
- `EXEMPT`、已签到以及已有情况填报记录分别处理，不用新的提交覆盖未知或既有记录。
